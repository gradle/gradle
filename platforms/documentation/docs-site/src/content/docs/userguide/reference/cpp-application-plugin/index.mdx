## Build variants

The C++ Application Plugin understands the following dimensions.
Read the <Xref page="building-cpp-projects" section="Introducing build variants">introduction to build variants</Xref> for more information.

<dl>
<dt>Build types - always either _debug_ or _release_</dt>
<dd>

The build type controls the debuggability as well as the optimization of the generated binaries.

- `debug` - Generate debug symbols and don’t optimized the binary
- `release` - Generate debug symbols and optimize, but extract the debug symbols from the binary

</dd>
<dt>Target machines - defaults to the build host</dt>
<dd>

The target machine expresses which machines the application expects to run.
A target machine is identified by its operating system and architecture.
Gradle uses the target machine to decide which tool chain to choose based on availability on the host machine.

</dd>
</dl>

### Variant-dependent Tasks

The C++ Application Plugin creates tasks based on the variants of the application component.
Read the <Xref page="building-cpp-projects" section="Introducing build variants">introduction to build variants</Xref> for more information.
The following diagram shows the relationship between variant-dependent tasks.

<Image src={cppApplicationVariantTaskGraph} alt="cpp application variant task graph" />

<dl>
<dt>`compile_Variant_Cpp` (e.g. `compileDebugCpp` and `compileReleaseCpp`)  - <GroovyDocLink class="org.gradle.language.cpp.tasks.CppCompile" /></dt>
<dd>

Depends on: All tasks that contribute source files to the compilation
::
Compiles C++ source files using the selected compiler.

</dd>
<dt>`link_Variant_` (e.g. `linkDebug` and `linkRelease`) - <GroovyDocLink class="org.gradle.nativeplatform.tasks.LinkExecutable" /></dt>
<dd>

Depends on: All tasks which contribute to the link executable, including `link_Variant_` and `create_Variant_` tasks from projects that are resolved via project dependencies
::
Links executable from compiled object files using the selected linker.

</dd>
<dt>`install_Variant_` (e.g. `installDebug` and `installRelease`) - <GroovyDocLink class="org.gradle.nativeplatform.tasks.InstallExecutable" /></dt>
<dd>

Depends on: `link_Variant_` and all tasks which contribute to the runtime of the executable, including `link_Variant_` tasks from projects that are resolved via project dependencies
::
Installs the executable and all of it’s runtime dependencies for easy execution.

</dd>
<dt>`assemble_Variant_` (e.g. `assembleDebug` and `assembleRelease`) - Task (lifecycle)</dt>
<dd>

Depends on: `link_Variant_`
::
Aggregates tasks that assemble the specific variant of this application.

</dd>
</dl>

### Lifecycle Tasks

The C++ Application Plugin attaches some of its tasks to the standard lifecycle tasks documented in the <Xref page="base-plugin" section="The Base Plugin">Base Plugin chapter</Xref> - which the C++ Application Plugin applies automatically:

<dl>
<dt>`assemble` - Task (lifecycle)</dt>
<dd>

Depends on: `linkDebug`
::
Aggregate task that assembles the debug variant of the application for the current host (if present) in the project.
This task is added by the <Xref page="base-plugin" section="The Base Plugin">Base Plugin</Xref>.

</dd>
<dt>`check` - Task (lifecycle)</dt>
<dd>

Aggregate task that performs verification tasks, such as running the tests.
Some plugins add their own verification task to `check`.
For example, the <Xref page="cpp-unit-test-plugin" section="C++ Unit Test">C++ Unit Test Plugin</Xref> attaches a task to this lifecycle task to run tests.
This task is added by the <Xref page="base-plugin" section="The Base Plugin">Base Plugin</Xref>.

</dd>
<dt>`build` - Task (lifecycle)</dt>
<dd>

Depends on: `check`, `assemble`
::
Aggregate tasks that perform a full build of the project.
This task is added by the <Xref page="base-plugin" section="The Base Plugin">Base Plugin</Xref>.

</dd>
<dt>`clean` - Delete</dt>
<dd>

Deletes the build directory and everything in it, i.e. the path specified by the `layout.buildDirectory` project property.
This task is added by the <Xref page="base-plugin" section="The Base Plugin">Base Plugin</Xref>.

</dd>
</dl>

## Dependency management

Just like the tasks created by the C++ Application Plugin, multiple configurations are created based on the variants of the application component.
Read the <Xref page="building-cpp-projects" section="Introducing build variants">introduction to build variants</Xref> for more information.
The following graph describes the configurations added by the C++ Application Plugin:

<Image src={cppApplicationConfigurations} alt="cpp application configurations" />

- The configurations in white are the ones a user should use to declare dependencies
- The configurations in pink, also known as consumable denoted by (C), are the ones used when a component runs against the library
- The configurations in blue, also known as resolvable denoted by (R), are internal to the component, for its own use

The following configurations are used to declare dependencies:

<dl>
<dt>`implementation`</dt>
<dd>

Used for declaring implementation dependencies for all variants of the main component.
This is where you should declare dependencies of any variants.

</dd>
<dt>`main_Variant_Implementation` (e.g. `mainDebugImplementation` and `mainReleaseImplementation`) extends `implementation`</dt>
<dd>

Used for declaring implementation dependencies for a specific variant of the main component.
This is where you should declare dependencies of the specific variant.

</dd>
</dl>

The following configurations are used by downstream consumers that depend on the application component:

<dl>
<dt>`_variant_RuntimeElements` (e.g. `debugRuntimeElements` and `releaseRuntimeElements) extends `main_Variant_Implementation`</dt>
<dd>

Used for executing the application.
This configuration is meant to be used by consumers, to retrieve all the elements necessary to run the application.

</dd>
</dl>

The following configurations are used by the application itself:

<dl>
<dt>`cppCompile_Variant_` (e.g. `cppCompileDebug` and `cppCompileRelease`) extends `main_Variant_Implementation`</dt>
<dd>

Used for compiling the application.
This configuration contains the compile include roots of the application and is therefore used when invoking the C++ compiler to compile it.

</dd>
<dt>`nativeLink_Variant_` (e.g. `nativeLinkDebug` and `nativeLinkRelease`) extends `main_Variant_Implementation`</dt>
<dd>

Used for linking the application.
This configuration contains the libraries of the application and is therefore used when invoking the C++ linker to link it.

</dd>
<dt>`nativeRuntime_Variant_` (e.g. `nativeRuntimeDebug` and `nativeRuntimeRelease`) extends `main_Variant_Implementation`</dt>
<dd>

Used for executing the application.
This configuration contains the runtime libraries of the application.

</dd>
</dl>

## Conventions

The C++ Application Plugin adds conventions for sources and tasks, shown below.

### Project layout

The C++ Application Plugin assumes the project layout shown below.
None of these directories need to exist or have anything in them.
The C++ Application Plugin will compile whatever it finds and ignore anything missing.

<dl>
<dt>`src/main/cpp`</dt>
<dd>

C++ source with extension of `.cpp`, `.c++` or `.cc`

</dd>
<dt>`src/main/headers`</dt>
<dd>

Headers - headers needed to compile the application

</dd>
</dl>

You <Xref page="building-cpp-projects" section="Customizing file and directory locations">configure the project layout</Xref> by configuring the `source` and `privateHeaders` respectively on the `application` script block.

### `link_Variant_` Task

Read the <Xref page="building-cpp-projects" section="Introducing build variants">introduction to build variants</Xref> for more information.
Some of the most common configuration options are shown below.

<dl>
<dt><GroovyDocLink class="org.gradle.nativeplatform.tasks.LinkExecutable" method="debuggable">debuggable</GroovyDocLink></dt>
<dd>

`true`

</dd>

<dd>

</dd>

</dd>

</dd>

### `install_Variant_` Task

The C++ Application Plugin adds a <GroovyDocLink class="org.gradle.nativeplatform.tasks.InstallExecutable" /> instance for each variant of the test component — e.g. `installDebug` and `installRelease`.
Read the <Xref page="building-cpp-projects" section="Introducing build variants">introduction to build variants</Xref> for more information.
There is no need to configure any properties on the task.
