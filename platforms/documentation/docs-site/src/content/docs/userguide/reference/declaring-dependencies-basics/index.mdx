## Types of dependencies

There are three main types of dependencies in Gradle:

1. **Module Dependencies**: Refer to libraries from external repositories.
2. **Project Dependencies**: Refer to other projects in the same multi-project build.
3. **File Dependencies**: Refer to local files or directories, such as `.jar` or `.aar` files.

### 1. Module dependencies

Module dependencies are the most common dependencies.
They refer to a published module by its coordinates (`group:name:version`).

Every dependency is added to a bucket configuration that defines its scope.

Use the single string `"group:name:version"` (you can also include classifier/extension if needed, e.g., `group:name:version:classifier@ext`):

<SampleScripts sample_name="external-dependencies" basename="build" tag="module-dependencies" source_dir="snippets/reference/dependency-management/declaring-dependencies/externalDependencies" />

:::caution
The map notation is deprecated and will be removed in Gradle 10. Prefer the single-string form.<br/>
For example: `runtimeOnly(group: 'org.springframework', name: 'spring-core', version: '2.5')`.<br/>
Should be: `runtimeOnly('org.springframework:spring-core:2.5')`.
:::

Module dependencies use the <JavaDocLink class="org.gradle.api.artifacts.ExternalModuleDependency" /> and <GroovyDocLink class="org.gradle.api.artifacts.dsl.DependencyHandler" /> APIs.
These APIs provide expose properties and configuration methods for defining dependencies such a `transitive`, `because`, and a `version {}` block for `strictly`, `prefer`, and `reject`.

### 2. Project dependencies

Project dependencies allow you to reference other projects within a multi-project Gradle build.

<Image src={dependencyManagementProjectDependencies} alt="dependency management project dependencies" />

This is useful for organizing large projects into smaller, modular components:

<SampleScripts sample_name="declaring-dependencies-project-dependencies" basename="build" subpath="web-service" tag="project-dependencies" source_dir="snippets/reference/dependency-management/declaring-dependencies/declaringDependencies-projectDependencies" />

Gradle uses the <GroovyDocLink class="org.gradle.api.Project" method="project(java.lang.String)">`project()`</GroovyDocLink> function to define a project dependency.
This function takes the relative path to the target project within the build.
The path is typically defined using a colon (`:`) to separate different levels of the project structure.

Project dependencies are automatically resolved such that the dependent project is always built before the project that depends on it.

#### Type-safe project dependencies

Type-safe project accessors are an incubating feature which must be enabled explicitly.
Implementation may change at any time.

To add support for type-safe project accessors, add `enableFeaturePreview("TYPESAFE_PROJECT_ACCESSORS")` this to your `settings.gradle(.kts)` file:

<SampleScripts sample_name="declaring-dependencies-type-safe-project-dependencies" basename="settings" tag="accessors" source_dir="snippets/reference/dependency-management/declaring-dependencies/declaringDependencies-typeSafeProjectDependencies" />

One downside of using the `project(":some:path")` notation is the need to remember project paths for dependencies.
Moreover, changing a project path requires manually updating every occurrence, increasing the risk of missing one.

Instead, the experimental type-safe project accessors API provides IDE completion, making it easier to declare dependencies:

<SampleScripts sample_name="declaring-dependencies-type-safe-project-dependencies" basename="build" subpath="web-service" tag="project-dependencies" source_dir="snippets/reference/dependency-management/declaring-dependencies/declaringDependencies-typeSafeProjectDependencies" />

With this API, incorrectly specified projects in Kotlin DSL scripts trigger compilation errors, helping you avoid missed updates.

Project accessors are based on project paths.
For instance, the path `:commons:utils:some:lib` becomes `projects.commons.utils.some.lib`, while kebab-case (`some-lib`) and snake-case (`some_lib`) are converted to camel case: `projects.someLib`.

### 3. File dependencies

File dependencies allow you to include external JARs or other files directly into your project by referencing their file paths.
File dependencies also allow you to add a set of files directly to a configuration without using a repository.

:::note
File dependencies are generally discouraged.
Instead, prefer declaring dependencies on an external repository, or if necessary, declaring a maven or ivy repository using a `file://` URL.
:::

<Image src={dependencyManagementFileDependencies} alt="dependency management file dependencies" />

File dependencies are unique because they represent a direct reference to files on the filesystem without any associated metadata, such as transitive dependencies, origin, or author information.

<SampleScripts sample_name="declaring-dependencies-file-dependencies" basename="build" tag="file-dependencies" source_dir="snippets/reference/dependency-management/declaring-dependencies/declaringDependencies-fileDependencies" />

In this example, each dependency explicitly specifies its location within the file system.
Common methods for referencing these files include:

- [`Project.files()`](link:__GRADLE_GROOVYDSL__/org.gradle.api.Project.html#org.gradle.api.Project:files(java.lang.Object[])): Accepts one or more file paths directly.
- <JavaDocLink class="org.gradle.api.file.ProjectLayout" method="files-java.lang.Object...-">`ProjectLayout.files()`</JavaDocLink>: Accepts one or more file paths directly.
- <GroovyDocLink class="org.gradle.api.Project" method="fileTree(java.lang.Object)">`Project.fileTree()`</GroovyDocLink>: Defines a directory and includes or excludes specific file patterns.

:::note
The order of files in a `FileTree` is not guaranteed to be stable, even on the same computer.
As a result, dependency configurations using `FileTree` may produce resolution results with varying order, which can impact the cacheability of tasks that use these results as inputs.
To ensure more predictable and stable behavior, it is recommended to use the simpler `files` method where possible.
:::

Alternatively, you can use a <Xref page="supported-repository-types" section="Flat directory repository">flat directory</Xref> repository to specify the source directory for multiple file dependencies.

Ideally, you should use Maven or Ivy repository with a local URL:

```groovy
repositories {
    maven {
        url = 'file:///path/to/local/files' // Replace with your actual path
    }
}
```

To add files as dependencies, pass a <Xref page="working-with-files" section="Using `FileCollection`">file collection</Xref> to the configuration:

<SampleScripts sample_name="external-dependencies" basename="build" tag="file-dependencies" source_dir="snippets/reference/dependency-management/declaring-dependencies/externalDependencies" />

Note that file dependencies are not included in the published dependency descriptor for your project.
However, they are available in transitive dependencies within the same build, meaning they can be used within the current build but not outside it.

You should specify which tasks produce the files for a file dependency.
Otherwise, the necessary tasks might not run when you depend on them transitively from another project:

<SampleScripts sample_name="generated-file-dependencies" basename="build" tag="generated-file-dependencies" source_dir="snippets/reference/dependency-management/declaring-dependencies/generatedFileDependencies" />

```bash
$ ./gradlew -q list
```

```text
compiling classes
classpath = [classes]
```

See more in the <Xref page="gradle-dependencies" section="Gradle distribution-specific dependencies">Gradle distribution-specific dependencies</Xref>.

## Documenting dependencies

When declaring a dependency or a <Xref page="dependency-constraints" section="Declaring Dependency Constraints">dependency constraint</Xref>, you can provide a reason to clarify why the dependency is included.
This helps make your build script and the <Xref page="viewing-debugging-dependencies" section="Identify the selected version using the `dependencyInsight` task">dependency insight report</Xref> easier to interpret:

<SampleScripts sample_name="inspecting-dependencies-dependency-reason" basename="build" tag="dependency-reason" source_dir="snippets/reference/dependency-management/declaring-dependencies/inspectingDependencies-dependencyReason" />

In this example, the <JavaDocLink class="org.gradle.api.artifacts.DependencyConstraint" method="because(java.lang.String)">`because()`</JavaDocLink> method provides a reason for including the `asm` library, which helps explain its purpose in the context of the build:

```bash
$ ./gradlew -q dependencyInsight --dependency asm
```
