# Exploratory build measurements: 2026-09-04

Production code: `ca75ed3ffb17a1ca33df5a413a10bb1704f6bf40`. No production code changed
for the cross-project tests or these measurements. See [method and reproduction](README.md)
and [all 96 samples](results-2026-09-04.json), including warmups. Full local build logs and
histograms are in `/tmp/property-provenance-build-measurements-20260904`; those large,
environment-specific files are not committed.

Linux aarch64, eight available CPUs, OpenJDK 25.0.4 Ubuntu, G1, 512 MiB initial/maximum
heap, two workers. Configuration cache, build cache, and filesystem watching disabled.
The IDE remained running; no Gradle test suite or JMH run ran alongside these measurements.
This is a development workstation experiment, not an isolated performance lab.

The fixtures have 10 / 50 Java subprojects, 40 four-property model tasks per project,
three extension properties per project, and a chain of Java project dependencies.
The main task graphs contain 461 / 2,301 tasks. Initial compilation and mode warmups
are excluded; subsequent Java compilation and jar tasks are up to date.

## Warm timing

Nine measured samples per mode after three rotating warmup rounds. Values are median
and observed min–max in milliseconds. Configuration means main-build `projectsLoaded`
through task-graph readiness; CLI wall time also includes startup/connection and task
execution/up-to-date checks.

| Projects | Mode | Configuration ms | CLI wall ms |
|---|---|---:|---:|
| 10 | Disabled | 42.4 (36.3–57.7) | 424.4 (407.1–452.3) |
| 10 | Origins | 48.3 (37.4–69.9) | 427.1 (412.7–476.4) |
| 10 | Locations | 41.8 (36.5–54.1) | 428.0 (408.1–455.5) |
| 50 | Disabled | 92.1 (80.3–123.1) | 626.5 (608.1–658.5) |
| 50 | Origins | 101.1 (75.3–126.7) | 629.3 (577.7–680.4) |
| 50 | Locations | 97.7 (78.9–119.6) | 645.1 (593.1–654.2) |

These do **not** establish a reliable slowdown percentage. Timing ranges overlap, and
configuration times continued declining during measurement. Rotating order reduces but
does not eliminate warmup/JIT/cache bias. Origin-only median CLI time differs by about
3 ms in both fixtures, below the observed variation. More warmup and independent daemon
repetitions are needed before treating the configuration-time differences as an effect.

## Configured-model live heap

Three separate post-full-GC histogram samples per mode, while the main build and task
graph remain reachable. Values are median and min–max in MiB (1,048,576 bytes).

| Projects | Mode | Whole-daemon live MiB | Median delta vs disabled |
|---|---|---:|---:|
| 10 | Disabled | 88.304 (88.235–88.312) | — |
| 10 | Origins | 88.432 (88.378–88.446) | +0.128 |
| 10 | Locations | 88.491 (88.486–88.498) | +0.187 |
| 50 | Disabled | 94.575 (94.556–94.583) | — |
| 50 | Origins | 95.219 (95.213–95.236) | +0.643 |
| 50 | Locations | 95.503 (95.497–95.512) | +0.927 |

In the 50-project origin-only samples, the histograms consistently contain 10,821
provenance states, 3,681 records, and 2,055 finalized snapshots. The fixture explicitly
creates 8,150 properties; Gradle's Java/buildSrc configuration accounts for additional
tracked properties. Location mode has the same state/snapshot counts but 15,931 records,
consistent with per-occurrence locations losing record sharing.

The shallow sum of provenance classes and their typed arrays is 625,472 bytes for
origins and 919,472 bytes for locations in the 50-project fixture, versus 1,112 bytes
in disabled mode. Disabled histograms contain no `PropertyProvenanceState` or snapshot
instances; their small fixed metadata includes the registry's unknown-record templates
and initialized enums. This also checks that an earlier enabled build's property states
are not still live at the disabled checkpoint in the reused daemon.

The whole-live-heap deltas and shallow sums are different measurements. Neither is an
exclusive retained-size/dominator analysis, and the shallow sums omit strings, registry
map entries, general-purpose arrays, and fields in property objects. The similar scaling
across these two workloads is encouraging, but does not predict all production builds.

## Cold-daemon smoke samples

One fresh-daemon sample per mode, retaining disk/script caches and up-to-date outputs:
10-project CLI time was 3.12 / 3.09 / 3.35 seconds for disabled / origins / locations;
50-project time was 3.72 / 4.07 / 4.06 seconds. One sample cannot establish a cold-start
regression. These are not cold-filesystem or fresh-checkout builds.

An earlier one-project harness smoke attempt lost its daemon without a useful error;
the second smoke attempt and this full measurement run succeeded. Neither smoke attempt
is mixed into these results.

## What remains unmeasured

- Compiled-in-but-disabled cost versus a matching build with the prototype removed.
  Comparing different released Gradle versions would not isolate that cost.
- A production build corpus, longer warmup, independent daemon repetitions, and
  repeated cold-start measurements.
- Peak heap, exclusive/dominator-retained sizes, large/long-lived finalized graphs,
  and builds dominated by other plugins, Kotlin DSL compilation, or actual compilation.
- Configuration-cache hits, because provenance persistence remains unimplemented.

The next performance step is a matching no-provenance baseline and repeated measurements
on a selected production build. The current evidence supports a sub-MiB incremental
live-heap cost for this 50-project workload, not a general performance guarantee.
